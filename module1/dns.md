# DNS: практика

## 1. dig google.com

Вывод :
google.com.  300  IN  A  142.250.185.78

- IP: 142.250.185.78
- TTL: 300 секунд
- Тип записи: A
- Сервер, который отвечал: 192.168.1.1#53

Разбор: запросил A-запись (IPv4) для google.com. Получил один IP. TTL 300 — 5 минут кэша.

## 2. dig ya.ru MX

Вывод (ANSWER SECTION):
ya.ru.  3600  IN  MX  10 mx.yandex.ru.

- MX-сервер: mx.yandex.ru
- Приоритет: 10 (чем меньше число — тем приоритетнее)
- TTL: 3600 секунд (1 час)

Разбор: MX-запись показывает, какой сервер принимает почту для домена. Если MX-записей несколько, письмо сначала идёт на сервер с меньшим приоритетом.

## 3. dig github.com A

Вывод (ANSWER SECTION):
github.com.  60  IN  A  140.82.121.4

- IP: 140.82.121.4
- TTL: 60 секунд

Разбор: маленький TTL — GitHub часто меняет адреса для балансировки.

## 4. dig +short google.com

Вывод:
142.250.185.78

Что показывает +short: только ответ, без служебных секций. Одна строка — IP. Удобно для скриптов, когда нужно распарсить IP программно.

Для MX с +short:
dig +short ya.ru MX
Вывод:
10 mx.yandex.ru.

## 5. nslookup github.com

Вывод:
Server:  192.168.1.1
Address: 192.168.1.1#53

Non-authoritative answer:
Name:  github.com
Address: 140.82.121.4

- IP: 140.82.121.4
- Сервер: 192.168.1.1

Чем отличается от dig:
- Меньше информации: не показывает TTL, не разделяет секции QUESTION/ANSWER.
- Меньше гибкости: нет ключей типа +short, +trace.
- Non-authoritative answer — ответ из кэша, а не напрямую от авторитетного сервера домена.
- В ИБ стандарт — dig, потому что он даёт больше данных и удобнее для скриптов.

## Вопрос 1. Что происходит при вводе google.com в браузере

Пошагово:

1. Браузер проверяет свой кэш DNS — может, IP уже сохранён с недавнего захода.
2. Проверяет системный кэш.
3. Если нет — спрашивает DNS-резолвер (обычно роутер, например 192.168.1.1).
4. Резолвер спрашивает корневой сервер "." — "где искать .com?"
5. Корневой отвечает: "иди к TLD-серверу .com".
6. TLD отвечает: "иди к авторитетному серверу google.com".
7. Авторитетный сервер возвращает IP: 142.250.185.78.
8. Резолвер кэширует ответ на TTL секунд и возвращает браузеру.
9. Браузер устанавливает TCP-соединение с этим IP на порт 443 (HTTPS).
10. Проходит TLS-рукопожатие, потом HTTP-запрос, потом ответ — страница отображается.

## Вопрос 2. Что такое TTL

TTL (Time To Live) — время жизни DNS-записи в секундах. Говорит резолверам и браузерам: "кэшируй этот ответ столько секунд, потом спроси заново".

Зачем нужен:
- Скорость: не надо каждый раз проходить весь путь DNS.
- Снижение нагрузки на DNS-серверы: миллионы запросов в секунду, без кэша они бы не выдержали.
- Гибкость: маленький TTL позволяет быстро менять IP (например, при балансировке или аварии), большой TTL — стабильность, но менять сложнее.

В ИБ: злоумышленники используют короткий TTL, чтобы быстро менять IP серверов и уходить от блокировок. Защитники анализируют TTL для выявления подозрительных доменов.

## Вопрос 3. Чем A отличается от CNAME

A-запись: домен → IPv4-адрес. Конкретный, числовой.
Пример: google.com. 300 IN A 142.250.185.78

CNAME (Canonical Name): домен → другой домен. Псевдоним.
Пример: www.github.com. 3600 IN CNAME github.com.

Когда браузер спрашивает www.github.com:
1. Получает CNAME: "это псевдоним github.com".
2. Идёт спрашивать github.com.
3. Получает A-запись: 140.82.121.4.
4. Соединяется.

Когда используют:
- A — когда есть конкретный IP.
- CNAME — когда хочешь, чтобы несколько поддоменов (www, mail, blog) указывали на один основной домен. Меняешь IP в одном месте — обновляется везде.

Ограничение: CNAME нельзя ставить на корневой домен (example.com), только на поддомены (www.example.com).

## Заметка: VPN и DNS

При включённом VPN команда dig возвращала:
connection timed out; no servers could be reached

Причина: VPN блокирует прямые DNS-запросы к внешним серверам, чтобы предотвратить утечки DNS (когда трафик шифруется, но DNS уходит напрямую провайдеру — это деанонимизирует пользователя).

Решение:
- Выключить VPN, когда делаешь задания по сетям.
- Или использовать явный DNS-сервер: dig @8.8.8.8 google.com.
